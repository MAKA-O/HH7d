# 01. Техническое задание

**Проект:** «Интеллектуальный тренажёр для подготовки к собеседованиям»
**Версия документа:** 1.0
**Статус:** действует
**Связанные документы:** [API-контракт](API.md), [Архитектура](02-Архитектура.md), [Сценарии](03-Сценарии.md), [Пояснительная записка](04-ПЗ.md), [Тестирование](05-Тестирование.md)

## 1. Основание для разработки

Разработка ведётся как учебный (дипломный) проект по направлению подготовки
в области программной инженерии. Основание — необходимость получить практический
инструмент подготовки к техническим собеседованиям, который сочетает реалистичную
имитацию интервью, автоматическую оценку развёрнутых ответов и объективную
аналитику прогресса, и при этом воспроизводимо работает в демонстрационном
окружении без платных внешних сервисов.

Заказчик и потребитель результата — соискатель, готовящийся к техническому
собеседованию (студент, выпускник, разработчик, меняющий стек или грейд).
Проверка результата выполняется в локальном окружении на контрольных сценариях
(см. раздел 8).

## 2. Назначение и цели

### 2.1. Назначение

Приложение — веб-тренажёр, который:

1. генерирует вопросы технического собеседования под выбранное направление,
   уровень и режим;
2. принимает развёрнутые текстовые (в том числе надиктованные голосом) ответы;
3. оценивает каждый ответ с помощью ИИ по формализованным критериям, объясняет
   ошибки и показывает эталонный ответ;
4. по завершении сессии формирует итоговый отчёт с вердиктом и рекомендациями;
5. поддерживает вспомогательные режимы: чат-консультацию по теории, задачи по коду
   с ИИ-ревью и аналитику прогресса;
6. гарантированно работает в двух режимах ИИ — с внешней моделью и без неё
   (офлайн-движок), с автоматическим переключением при сбоях.

### 2.2. Цели разработки

| Цель | Измеримый признак достижения |
|---|---|
| Ц-1. Сократить разрыв между «знаю теорию» и «умею отвечать на собеседовании» | Пользователь проходит полный цикл «вопрос → ответ → разбор → повтор», получая баллы и рекомендации по каждой теме |
| Ц-2. Сделать оценку ответа объяснимой, а не сводящейся к одной цифре | Каждая оценка содержит 4 критерия, сильные стороны, пробелы, эталонный ответ, рекомендацию и уточняющий вопрос |
| Ц-3. Обеспечить объективный контроль прогресса | Дашборд и `/api/analytics/overview` показывают динамику оценок, слабые и сильные темы, стрик занятий |
| Ц-4. Обеспечить работоспособность без платных сервисов и без сети | Полный сценарий проходит в режиме `offline` с детерминированным движком; переключение прозрачно для пользователя |
| Ц-5. Поддержать несколько ИТ-направлений и уровней | 6 направлений, 4 уровня, 3 режима, темы из справочника; банк вопросов покрывает все направления |
| Ц-6. Сделать приложение развёртываемым одним процессом | Собранный фронтенд раздаётся тем же `uvicorn`, что и API; исходные данные хранятся в SQLite |

## 3. Термины и определения

| Термин | Определение |
|---|---|
| Сессия (собеседование) | Запись `interview_sessions` — попытка прохождения интервью с набором вопросов, ответами и итоговым отчётом |
| Вопрос | Запись `questions`, привязанная к сессии; тип `theory` или `code` |
| Ответ | Запись `answers` — текст ответа пользователя на конкретный вопрос (не более одного на вопрос) |
| Оценка | Запись `evaluations` — результат ИИ-разбора ответа: балл, критерии, сильные стороны, пробелы, эталон |
| Критерии | `correctness`, `completeness`, `depth`, `clarity` — целые или дробные значения 0–10 |
| Отчёт сессии | JSON `session.report` со сводным баллом, вердиктом, сильными/слабыми темами, рекомендациями |
| Live-движок | Реализация `AIService` поверх внешней LLM (OpenAI-совместимый HTTP API, Ollama) |
| Offline-движок | Детерминированная реализация `AIService` без сети: банк вопросов + эвристики оценки |
| Fallback | Автоматическое переключение Live → Offline при ошибке внешней модели |
| Стрик | Число последовательных дней подряд с хотя бы одним оценённым ответом |
| Адаптивный вопрос | Дополнительный вопрос, подобранный по слабым темам текущей сессии |

## 5. Нефункциональные требования

### 5.1. Производительность

| ID | Требование |

### 5.3. Безопасность

| ID | Требование |
|---|---|
| NFR-9 | Пароли хранятся только как PBKDF2-SHA256-хеш со случайной солью; проверка — через `hmac.compare_digest` (защита от timing-атак) |

| NFR-11 | Каждый пользовательский запрос к объектам (сессии, вопросы, ответы, диалоги, задачи, ревью) фильтруется по `user_id`; доступ к чужому объекту — `404` (не раскрывается факт существования) |

## 6. Ограничения

| ID | Ограничение | Следствие |
|---|---|---|
| O-1 | Версия 1.0 — однопользовательская по модели данных, без ролей и администрирования | Нет панели администратора, модерации и общих (публичных) наборов вопросов |
| O-2 | Оценка ответа выполняется языковой моделью/эвристиками и не является юридически значимой | В интерфейсе оценка подаётся как тренировочная обратная связь |
| O-3 | Код пользователя не исполняется и не тестируется | Ревью анализирует текст решения, а не результаты его запуска |
| O-4 | Нет миграций БД (используется `create_all`) | Изменение схемы в версии 1.0 требует пересоздания базы или ручной миграции |
| O-5 | Синхронная обработка запросов в одном процессе `uvicorn` | Приложение рассчитано на демонстрационную и личную нагрузку, не на промышленный масштаб |
| O-6 | Внешняя LLM — неконтролируемая зависимость (доступность, стоимость, изменчивость ответов) | Предусмотрен fallback на офлайн-движок; результаты Live-режима не гарантируют детерминизм |
| O-7 | Серверное распознавание речи зависит от поддержки провайдером `/audio/transcriptions` | При недоступности используется браузерный Web Speech API |
| O-8 | Резюме пользователя передаётся в промпт внешней модели при Live-режиме | Пользователь должен осознавать это при заполнении резюме |
| O-9 | Интерфейс и ИИ-промпты ориентированы на русский язык | Качество ответов на других языках не гарантируется |

## 8. Критерии приёмки

Приёмка выполняется в локальном окружении на чистой базе данных. Результат
считается принятым, если одновременно выполнены все условия.

| ID | Критерий | Способ проверки |
|---|---|---|
| AC-1 | Приложение запускается одной командой `uvicorn app.main:app`; `GET /api/health` возвращает `status: "ok"` и корректные `app`, `version`, `ai_mode`, `ai_provider` | Ручная проверка, `smoke_check.py` |
| AC-2 | Swagger доступен по `/api/docs`, схема OpenAPI — по `/api/openapi.json` | Ручная проверка |
| AC-3 | Полный сценарий без ключа API проходит: регистрация → профиль → создание собеседования → ответ → ИИ-оценка (4 непустых критерия, балл 0–10) → завершение → отчёт → аналитика | `scripts/smoke_check.py`, тесты |
| AC-4 | Живой режим включается заданием `AI_API_KEY`; `GET /api/ai/health` возвращает `mode: "live"` и `available: true`, а при отзыве ключа/имитации сбоя система продолжает работать в `offline` | Ручная проверка с ключом и без него |
| AC-5 | Чат работает в обоих режимах (`stream: false`/`stream: true`), события SSE соответствуют контракту | Тест-кейсы TC-5.2, TC-5.3 |
| AC-6 | Генерация задачи и код-ревью работают без ключа; ревью содержит непустой вердикт, оценку 0–10 и список замечаний | Тест-кейс TC-6.3 |
| AC-7 | Данные изолированы по пользователям: доступ к чужим сессиям/диалогам/задачам — `404`; без токена — `401` | Тест-кейсы TC-1.5, TC-3.5, TC-5.5 |
| AC-8 | `npm run build` во `frontend/` завершается без ошибок TypeScript и размещает `index.html` и хэшированные файлы `index-*.js` / `index-*.css` в `backend/app/static`; после запуска `uvicorn` интерфейс открывается на `http://127.0.0.1:8000/` и клиентские маршруты не дают 404 | Ручная проверка сборки и SPA-навигации |
| AC-9 | `python -m pytest -q` из `backend/` — все тесты проходят (кроме явно пропущенных с обоснованием) | Запуск тестов |
| AC-10 | Документация из раздела 7 присутствует, соответствует коду по названиям эндпоинтов, таблиц и полей, содержит mermaid/ASCII-диаграммы и перекрёстные ссылки | Ревизия документации |
| AC-11 | Демо-аккаунт `demo@trainer.ru` / `demo1234` создаётся скриптом `backend/scripts/seed_demo.py`, повторный запуск не дублирует данные | Запуск скрипта дважды |
| AC-12 | Секреты не хранятся в репозитории: `.env` отсутствует в git, в `.env.example` ключи пустые | `git status`, ревизия `.gitignore` |
| AC-13 | Интерфейс полностью на русском, адаптивен, отображает режим ИИ, корректно обрабатывает ошибки и пустые состояния | Ручная проверка UX |

## 11. Порядок изменения требований

Изменение функциональных требований, затрагивающее API, допускается только после
обновления [контракта API](API.md) и согласования с обеими частями системы
(бэкенд и фронтенд). Изменения, затрагивающие схему БД, требуют обновления
[архитектуры](02-Архитектура.md) и описания миграции. Все изменения фиксируются
в истории версий документа.
